# Структура «УниМаркета»

Актуальное решение согласовано 22 октября 2026: одна самостоятельная HTML-страница на файл, CSS и JavaScript отдельно, без сборки HTML. Прежняя схема src/pages + partials + public отменена.

29 октября подключён backend: router.php → backend/auth.php → AuthHandler и PDO → MySQL 8.4. Текущая схема на 7 таблиц — database/schema.sql; описание и DML — database/README.md. Требования — только docs/mvp/SPECIFICATION.md; ответственность реальных файлов — learning/PROJECT_MAP.md.

## Структура

Строки с пометкой «создаём по мере реализации» — планы этапов 3–9, а не существующие файлы; точные имена уточняются на своём этапе.

## HTML и просмотр

Весь лендинг редактируем в корневом index.html. Новую страницу создаём целиком в pages/ соответствующего раздела. У каждой страницы свои head, header, main и footer; HTML-вставок и сгенерированных копий нет.

Запуск — Open Server Panel 6: модули Apache, PHP-8.3 и MySQL-8.4, проект unimarket.local (http://unimarket.local). Папка проекта в панели — ссылка на репозиторий, потому что панель не принимает пробелы в пути. Первичная подготовка — php scripts/init-db.php. Открытие HTML напрямую или через Live Server не выполняет сессии и API. Node.js не является зависимостью приложения; сборка не нужна.

Пути считаем относительно конкретного HTML-файла. В index.html иконка подключается как assets/icons/имя.svg, страница входа — pages/auth/login.html. В pages/auth/login.html путь к общей иконке начинается с ../../assets/, к лендингу — ../../index.html. Не переносить одинаковый относительный путь на другую глубину без проверки.

## Стили и JavaScript

Сначала подключаем assets/css/base.css, затем CSS текущей страницы. В base лежат шрифт, смысловые переменные, базовые правила и контейнер. В landing.css — секции лендинга и media-запросы. Правила компонента и его адаптации находятся рядом.

При появлении повторяемых элементов можно выделить общий CSS компонента. Не дробить правила только из-за количества строк. Обычный CSS достаточен; SCSS не обязателен.

JavaScript добавляем только для нужного поведения и подключаем отдельным файлом. Для простого действия используем функцию; класс нужен для связанных операций с собственным состоянием. FAQ уже работает через details/summary без JS.

Лендинг работает без JavaScript: две ссылки аккаунта всегда видны в одном nav. До 600px CSS показывает иконки входа и регистрации вместо текста; доступные названия сохраняются через aria-label. Кнопка регистрации в приветствии до 600px имеет ширину плашки баллов. Карточки на телефоне используют Flexbox: одна колонка до 600px, две с переносом на 600–767px. Их мобильная min-height обнулена, поэтому высоту определяет содержимое.

## Принципы

- Обязателен навык ponytail на уровне full (уровень навыка, не git-ветка); KISS и DRY, короткий читаемый код.
- Жёсткого предела строк нет. 300–400 строк понятного HTML одной страницы допустимы.
- Не склеивать операции и не минифицировать исходники ради краткости.
- Разделять файлы по ответственности и удобству, не ради счётчика.
- Небольшое повторение шапки/подвала между HTML-страницами допустимо на текущем этапе.
- Комментарии писать на русском, пояснять причину, а не пересказывать очевидное.
- Сохранять семантику, клавиатуру, видимый фокус и обработку ошибок.
- Главная: Grid на компьютере/планшете, Flexbox через media-запросы на телефоне.
- Корзины нет: материал приобретается со страницы описания.

## Backend

backend/bootstrap.php отвечает за PDO, сессии и ответы; AuthHandler.php — за операции регистрации и входа; auth.php — за GET/POST /api/auth, CSRF, валидацию и ошибки. Регистрация создаёт users и wallets в транзакции, затем обновляет идентификатор сессии. Структура БД применяется CLI-скриптом, а приложение подключается отдельным пользователем с правами только на данные.

.htaccess отдаёт напрямую только ресурсы assets, остальные запросы идут в router.php: он разрешает известные страницы и API, а config, backend, scripts, database и storage закрыты ответом 404. config/local.php и storage игнорируются Git. При размещении нужен Apache с mod_rewrite и AllowOverride, иначе .htaccess не сработает и закрытые папки откроются.

## Текущее состояние

Регистрация только по логину и паролю сразу создаёт авторизованную сессию; email и восстановление исключены. Вход и регистрация находятся в pages/auth/login.html; #registraciya выбирает регистрацию. auth.js в head выбирает data-ekran до отрисовки, после DOMContentLoaded получает CSRF и подключает отправку в PHP. Восстановление удалено.

Лендинг использует base.css и landing.css, формы — base.css и auth.css. Закрытая pages/catalog.html загружает account.js и catalog.css, показывает логин и остатки из БД и кнопку выхода. Это начальная страница, без имитации работающего магазина. Manrope хранится локально с лицензией OFL. Адаптация разработана независимо от мобильных макетов Figma. Фактические проверки и следующий шаг — только в PROGRESS.md.

## Ветки и порядок работы

- `mvp` — рабочая ветка. Этапы 3–9 из learning/PROGRESS.md пишутся здесь; после каждого завершённого этапа ставится аннотированный тег `mvp-etap-N` (`git tag -a mvp-etap-3 -m "Этап 3: публикация"`).
- Участники работают в своих ветках от `mvp` и вносят изменения через pull request в `mvp`. Прямые коммиты в `mvp` делает только владелец.
- `full` — полный первоначальный замысел и всё остальное. Обновляется только слиянием `mvp` → `full`: никогда не `full` → `mvp` и без rebase. Нужный файл из `full` переносится в `mvp` командой `git checkout full -- путь` отдельным коммитом.
- `main` — отдельная ветка для будущего pull request, сейчас пустая.
