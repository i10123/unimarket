## Что можно сохранить

- Общая модель из 17 таблиц соответствует полному объёму приложения. Это не минимальный набор для первого этапа и не доказательство необходимости каждой таблицы до реализации сценария.
- Кошелёк отдельно от аккаунта, единая история изменений баллов, уникальные пары для покупки и избранного, отзывы через покупку/заказ — понятные решения.
- Для повторного выбора исполнителя после отмены UNIQUE orders.request_id действительно мешает. Это ограничение было в моём исходном предложении; вопрос уже отмечен в DATABASE_REVIEW.md, раздел 8.5.
- Вариант без UNIQUE(request_id) работоспособен, если все пути создания/отмены заказа блокируют строку заявки и проверяют её актуальное состояние. Одного снятия UNIQUE недостаточно. Это кандидат для итоговой модели, не внесённое изменение схемы.
- CHECK для взаимоисключающих источников чата и операции баллов полезен при поддерживаемой версии сервера.
- Индексы следует сопоставлять с реальными запросами; EXPLAIN и замеры ещё нужны. Внедрять все индексы из консультации автоматически не требуется.

## Технические уточнения к объяснениям

1. **CHECK и версия.** В MySQL ограничения CHECK реально исполняются с 8.0.16; формулировка «8.0+» недостаточно точна. Нельзя проверить наличие покупок в другой таблице через обычный CHECK строки material_files. Нужен согласованный серверный сценарий изменения файлов с блокировками; простое архивирование не запрещает UPDATE/DELETE файлов. [Документация CHECK](https://dev.mysql.com/doc/refman/8.0/en/create-table-check-constraints.html).
2. **CASCADE и состояния.** ON DELETE CASCADE выполняется при физическом удалении родителя. Изменение status на blocked или archived само не удаляет избранное. Объяснения таблицы в разделе 1.10 смешивают эти операции. [Документация внешних ключей](https://dev.mysql.com/doc/refman/8.0/en/create-table-foreign-keys.html).
3. **Тип связи файлов.** В разделе 2.1 написано «файлы M:N к материалу». В предложенной material_files с одним material_id связь material → files является 1:N. Для M:N понадобилась бы промежуточная таблица, которая сейчас не нужна. Между заявкой и откликами также 1:N; M:N — между исполнителями и заявками через отклики.
4. **Обязательность в ER-диаграмме.** Модератор материала может отсутствовать до решения; у чата ровно один из двух источников; у записи баллов ровно один из трёх источников. В диаграмме агента некоторые из этих ссылок ошибочно выглядят обязательными одновременно. Сохранить nullable-ссылки и соответствующие CHECK.
5. **Проверка остатков.** SUM по пустой истории даёт NULL, а не 0; для нового кошелька нужны COALESCE(SUM(...), 0). Агрегат сам по себе не проверяет полноту пар списания/начисления. [Документация агрегатов](https://dev.mysql.com/doc/refman/8.0/en/aggregate-functions.html).
6. **Обычное чтение профиля.** При стандартном REPEATABLE READ обычный SELECT использует снимок и не блокируется записью так, как предполагает обоснование кошелька в разделе 1.2. Отдельная wallets всё равно полезна по ответственности и для конкурирующих записей. [Документация уровней изоляции](https://dev.mysql.com/doc/refman/8.0/en/innodb-transaction-isolation-levels.html).
7. **Индексы.** Составной индекс с первым status может помогать фильтрации по status без subject_id/course; но он не обеспечивает автоматически нужную сортировку по дате при пропущенных средних полях. Динамическая сборка только нужных условий не требует индекса для каждой возможной комбинации. Подбор — по частым запросам и EXPLAIN. [Документация составных индексов](https://dev.mysql.com/doc/refman/8.4/en/multiple-column-indexes.html).
8. **Повтор покупки после архивации.** purchaseMaterial проверяет published до поиска уже существующей покупки. Поэтому повтор запроса после архивации вернёт ошибку, хотя покупка уже состоялась. Разделить проверку существующего результата и условия новой покупки; доступ к старой покупке не должен зависеть от возможности новой продажи.

При deadlock InnoDB может откатить всю транзакцию; приложение должно уметь повторить её целиком. [Документация MySQL](https://dev.mysql.com/doc/refman/8.4/en/innodb-error-handling.html). PDO::rollBack без активной транзакции выбрасывает исключение. [Документация PHP](https://www.php.net/manual/en/pdo.rollback.php).

## Что осталось решением владельца проекта

- **Награда.** В начале консультации сказано «за первую публикацию — 100 баллов», далее встречается «за публикацию», а ключ события привязан к материалу. Награда один раз на пользователя и один раз на одобренный материал — разные правила. Размер, частоту награды и передачу баллов от продажи автору пока не фиксировать как утверждённые.
- **Бесплатные материалы.** Исходная модель допускает цену 0, но требует ненулевого изменения в point_entries. Пример покупки пишет две нулевые записи и нарушит это ограничение. Нужно либо разрешить бесплатную покупку без записей движения баллов, либо явно потребовать положительную цену. Это несогласованность правил моей исходной модели и последующего примера, которую нужно устранить перед DDL.
- **Повторный заказ после отмены в том же обсуждении.** Снятие UNIQUE(request_id) не снимает UNIQUE(chat_id) и UNIQUE(response_id). Новый исполнитель с другим откликом допустим, но повторное назначение прежнего после отмены в текущей модели отдельно не решено.
- **Оценка услуги.** Хранить отзыв через выполненный заказ правильно; это не запрещает показывать агрегированный рейтинг и отзывы на странице объявления услуги. Нужный способ отображения ещё предстоит определить.
